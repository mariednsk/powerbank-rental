# ADR-004: Kafka + Transactional Outbox / Inbox

## Контекст

События `RentalStarted` и `RentalCancelled` должны доходить до подписчиков даже при временной недоступности брокера. Запись статуса в БД и отправка в брокер не образуют общую атомарную транзакцию. Брокер также может повторно доставлять сообщения.

## Рассмотренные варианты

1. Прямая синхронная отправка уведомлений из Rental Service — связывает критический процесс с необязательными подписчиками.
2. Записать статус в БД, затем отправить событие без Outbox — событие может потеряться при падении между действиями.
3. **Kafka + Transactional Outbox / Inbox** — состояние и запись события атомарны локально, публикация и обработка повторяемы.


## Решение

Выбрать вариант 3 — Kafka + Transactional Outbox / Inbox.

Все сервисы, публикующие критически важные события (Rental Service, Inventory Service, Payment Service и Station Gateway), используют Transactional Outbox.

Изменение бизнес-состояния и запись исходящего события в Outbox сохраняются в одной локальной транзакции соответствующей базы данных.

Отдельный обработчик публикует события из Outbox в Kafka. При временной недоступности брокера публикация повторяется после восстановления соединения.

Получатели используют `eventId`, Inbox и бизнес-ограничения для защиты от повторной обработки сообщений.

Для событий одной аренды используется ключ партиционирования `rentalId`. Порядок сообщений гарантируется только в рамках одной партиции одного топика. Поэтому получатели дополнительно проверяют допустимость переходов состояний.

Kafka используется для асинхронной передачи событий, но не является единственным хранилищем бизнес-состояния.

## Последствия

**Плюсы:** нет потери события при падении между commit и publish; подписчики развязаны; возможна повторная доставка. **Минусы:** инфраструктура и мониторинг Outbox; eventual consistency; дедупликацию нужно реализовать во всех важных consumer. Kafka сама по себе не гарантирует ровно один внешний бизнес-эффект.
