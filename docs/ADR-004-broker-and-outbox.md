# ADR-004: Kafka + Transactional Outbox / Inbox

## Контекст

События `RentalStarted` и `RentalCancelled` должны доходить до подписчиков даже при временной недоступности брокера. Запись статуса в БД и отправка в брокер не образуют общую атомарную транзакцию. Брокер также может повторно доставлять сообщения.

## Рассмотренные варианты

1. Прямая синхронная отправка уведомлений из Rental Service — связывает критический процесс с необязательными подписчиками.
2. Записать статус в БД, затем отправить событие без Outbox — событие может потеряться при падении между действиями.
3. **Kafka + Transactional Outbox / Inbox** — состояние и запись события атомарны локально, публикация и обработка повторяемы.

## Решение

Выбрать вариант 3. Rental Service в одной транзакции записывает новый статус и строку Outbox; отдельный публикационный процесс отправляет событие в Kafka и отмечает доставку. Kafka хранит события, подписчики (например, Notification Service) используют `eventId` и Inbox/уникальный ключ для дедупликации. Для порядка событий одной аренды применяется ключ партиционирования `rentalId`.

## Последствия

**Плюсы:** нет потери события при падении между commit и publish; подписчики развязаны; возможна повторная доставка. **Минусы:** инфраструктура и мониторинг Outbox; eventual consistency; дедупликацию нужно реализовать во всех важных consumer. Kafka сама по себе не гарантирует ровно один внешний бизнес-эффект.
