# ADR-002: Собственная база данных у сервиса

## Контекст

Разные сервисы должны независимо управлять своими инвариантами. Если Rental напрямую обновляет таблицу Inventory или Payment, нарушается ответственность сервиса; общая SQL-транзакция всё равно не распространится на платёжного провайдера и оборудование.

## Рассмотренные варианты

1. Общая БД и общие таблицы.
2. Одна СУБД, но отдельные схемы и права сервисов.
3. Отдельная логическая БД на сервис и доступ только через его контракт.

## Решение

Использовать вариант 3. Можно разместить логические БД на одном PostgreSQL-кластере, но **ни один сервис не читает и не изменяет чужие таблицы напрямую**. Состояние аренды — Rental DB; устройство и резерв — Inventory DB; платежи и ключи идемпотентности — Payment DB. Синхронизация — API и события.

## Последствия

**Плюсы:** локальные ACID-транзакции; независимость моделей; понятная собственность над данными. **Минусы:** нет межсервисных JOIN и распределённого ACID; нужны Saga, события и обработка eventual consistency.
